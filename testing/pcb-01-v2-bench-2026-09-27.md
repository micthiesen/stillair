## Scope and continuation

The bench task passed within the scope above. Full V2 qualification is not claimed. No motor
command, rail probing, analog overspeed calibration, sensor calibration, cold power-cycle
readback, two-cable/two-orientation USB check, unpowered USB back-feed check, or interrupted-flash
recovery test was performed. Existing V1 results remain attributed to V1.

Next: pair the new controller to Apple Home and let Michael install it using the saved loaded
configuration. Firmware always powers up off and requires a fresh user command after safe boot.
EEPROM settings and paired Matter credentials are designed to persist across power loss; a cold
power-cycle check on this V2 has not yet been observed. Final loaded tuning stays deferred by
Michael's instruction.

## Tooling observations

- The first serial open returned `Device or resource busy`; a subsequent open succeeded and no
  competing reader was found. No cause was established.
- `check_board_usb.py` reported no VID/PID device despite the immediately subsequent successful
  native ROM connection. Its I/O Registry result is unresolved and must not override actual

- The first flash wrote the image but failed its requested watchdog reset because ESP32-C6 does
  not support that espflash option. Repeating with `--before usb-reset --after hard-reset` verified

## Apple Home pairing follow-up

Michael reached the uncertified-accessory confirmation, accepted it, and then received
`Pairing Failed`. The [raw serial excerpt](pcb-01-v2-bench-2026-09-27/pairing-failed.log)
shows successful attestation, CSR, trusted-root and NOC installation, followed by joining the
intended 2.4 GHz network and obtaining `10.10.1.21`. The initial signal was -63 dBm. The final
177-second fail-safe expired for tentative fabric 1; the expected `Got Commissioning Complete
Request` and `Commissioning complete, fabric and network settings persisted` messages never
appeared. Failure is in the operational-network handoff, not the uncertified-accessory warning.
The exact cause remains unresolved.

From the Mac at `10.10.1.90`, Bonjour resolved the board's commissionable service to
`206EF112A5B00000.local.:5540`, IPv4 `10.10.1.21`, and IPv6
`fe80::226e:f1ff:fe12:a5b0%en0`. Three IPv4 and three IPv6 echo probes received no replies;
IPv4 ARP remained incomplete. These are observations, not proof of an AP-isolation fault or
firmware defect. The first operational-service browse happened after rollback, so absence of a
board operational service then cannot establish its availability during the failed attempt.
Packet capture was unavailable because the process lacked BPF-device permission.

A new raw serial capture and operational Bonjour browse were started for a requested retry.
That retry supplied **`SyNet`**, unlike the first attempt's **`SyNet-2G`**. The radio reported
`DisconnectedInfo { ssid: "SyNet", bssid: [0, 0, 0, 0, 0, 0], reason: NoAccessPointFound,
rssi: -128 }`, which the driver maps to `NoNetworkInterface`. `Wifi already connected,
disconnecting first` is normal retry handling, not evidence of a stale-state bug. The retry's
cause is therefore a network the C6 could not find; it does not explain the first attempt's
post-join timeout.

The ESP was reset through native USB, verified the saved MCF image at target `0x01`, and reopened
BLE commissioning. Michael kept the iPhone on **SyNet-2G** for subsequent attempts. No EEPROM
or firmware changes were made during this initial diagnosis. Build comparisons follow below.

## Build-profile comparison

Michael confirmed that V1 paired on this network and asked whether changing from MINI to WROOM
needed different firmware. Both modules use ESP32-C6 and a 40 MHz crystal. V2's ALARM input is
already GPIO10, and espflash detects the N8 module's 8 MB flash. The module swap does not select
a different CPU target or Matter implementation.

Comparison with the successful V1 revision `1633433` found no changes to `matter.rs`, app
`Cargo.toml`, app `Cargo.lock`, or executor priorities/heap/Matter allocation. The new low-rate
RSSI sampler is the only added periodic radio API call; no evidence currently implicates it.
The V1 bench workflow used `cargo build`, whereas the initial V2 flash in this session used
`cargo build --release`. The dev profile optimizes esp-radio at level 3; release uses level `s`.
Both levels are supported by the pinned esp-radio build script, so this is a diagnostic comparison,
not an established cause.

The unchanged-source **dev-profile** build was flashed successfully at
2026-09-28 01:28 UTC. ELF SHA-256:
`6892d5de13f979f10bfe9f605e4f810016b212364014681dd354f7444b4c68a6`.
The [dev flash receipt](pcb-01-v2-bench-2026-09-27/flash-dev.log) records the same C6 revision v0.2
and 8 MB flash. No NVS erase or MCF configuration write was performed. Boot re-verified the saved
image; the expected MCF watchdog fault after the flash pause cleared with `fault clear`, then the
normal safe-boot hold reached `idle_off` with clean MCF status. A fresh SyNet-2G pairing attempt
failed again. Michael moved close to the AP and confirmed the iPhone was on 2.4 GHz. The log
confirmed SyNet-2G, excellent -48 dBm RSSI, DHCP at `10.10.1.21`, and the same fail-safe timeout
without commissioning completion. The profile change did not fix pairing.
See the [dev pairing capture](pcb-01-v2-bench-2026-09-27/pairing-dev.log).

## Sequential commissioning experiment

The firmware briefly used the pinned stack's supported `run()` path instead of `run_coex()`, releasing
BLE before Wi-Fi starts. The arena grew from 20,000 to 32,000 bytes for the larger futures.
This tests radio coexistence as a cause of the handoff timeout; it is not an established fix.
Upstream notes Alexa incompatibility for this mode; the requested controller is Apple Home.

The first sequential build exposed a separate bug in `wifi_diag`: its five-second initial RSSI
sample called `esp_wifi_sta_get_rssi` before Wi-Fi initialization and panicked at
`current_task_is_wifi_task`, with `Load access fault (5)`, `mtval=0x000000a4`.
The sampler now mirrors the pinned safe `WifiController::rssi()` wrapper: call
`esp_wifi_get_mode` first and only read RSSI after a successful STA/APSTA mode result.
The mode query explicitly supports an uninitialized driver. No await separates the two calls,
so Matter cannot drop its controller between them on the shared thread executor. This fixes the
observed diagnostic-build boot failure; it does not establish the earlier pairing timeout's cause.

The corrected dev image was flashed at 2026-09-28 01:46:59 UTC, SHA-256
`60317c6dedb68208f3d4473eaca31c45c664008d054e7b212b2714cd996d054e`.
Formatting, clippy with warnings denied in both workspaces, all 234 host tests, and the app build
passed. Focused source review confirmed the API and FFI signatures. The corrected image booted
past the previous crash, advertised BLE commissioning, and showed 24,164 bytes allocated in the
32,000-byte arena during BLE-only startup. Nine unavailable RSSI polls completed without a crash;
`fault clear` cleared the post-flash MCF watchdog fault and the board reached `idle_off`.
No NVS erase or MCF image change was performed.

Michael's retry failed immediately. The log showed successful AddNOC, followed by
`Error invoking command: InvalidAction`, then the phone disconnected before any Wi-Fi scan or
join. The pinned sequential `WirelessNetCtl::Commissioning::scan()` explicitly returns
`InvalidAction`; earlier Apple attempts scanned immediately after AddNOC. This strongly indicates
that Apple's ScanNetworks request hit that stub, but the failing command ID was not logged.
The experiment did not solve pairing. Concurrent mode and the 20,000-byte arena were restored,
retaining the confirmed RSSI initialization fix.
See the [sequential pairing capture](pcb-01-v2-bench-2026-09-27/pairing-sequential.log).

## Transport diagnosis in progress

The optional `matter-diagnostics` build feature enables only `rs_matter::transport` DEBUG headers
on USB, retaining INFO elsewhere and disabling TRACE. The resolved dependency feature tree was
checked: `debug-tlv-payload` is absent. Default and diagnostic builds both pass clippy with
warnings denied and build successfully. Review confirmed logger filtering and packet-header-only
output. The new capture should distinguish missing operational packets from an incomplete CASE
exchange instead of inferring either from INFO-only logs.

At Michael's request, both the product name and mDNS commissioning name changed to `Stillair`.
These static details do not come from the persisted node label. The pinned stack hardcodes its
BLE local name to `BT`, so Apple Home's initial discovery tile may still show a generic type.
The concurrent diagnostic image with these names was flashed at 2026-09-28 01:53:46 UTC;
ELF SHA-256 `5916be19ebb1b687c40d914f3aa4455dc116e8b0ebdc4766d464e0b2adf41b4a`.
It booted and, after clearing the post-flash watchdog fault, returned to `idle_off`, `fault=null`,
`config=verified`. Michael's retry failed with Home's "Connect to a 2.4 GHz wifi and try again"
message, despite confirmed association to SyNet-2G. The packet capture shows BLE provisioning
and a successful connect response, but no received operational Matter packet over UDP. The
serial dropped-line count stayed at 23 before and after provisioning, so no additional dropped
output explains the missing handshake. The 177-second fail-safe expired and removed fabric 1.

During that attempt, operational service `00A24DE50CF9BB3D-00000000489422F0` resolved to the
board's `206EF112A5B00000.local.:5540`. Commissionable service `A9BFEC3B54CEB19B` resolved to the
same host with **`DN=Stillair`**, confirming the requested advertisement name on the LAN. Both
IPv4 `10.10.1.21` and IPv6 `fe80::226e:f1ff:fe12:a5b0%en0` resolved. Two IPv4 and two IPv6 pings
failed; IPv4 ARP remained incomplete. A fresh legacy-unicast mDNS query also received no reply
within four seconds. Discovery visibility alone does not prove unicast reachability.

Source inspection found that normal GATT disconnection resumes advertising without dropping the
Embassy network runner; ARP/NDP processing is independent of Matter's UDP/BTP receive selection.
Neither AP isolation nor a radio RX/TX failure is established. Michael confirmed UniFi and

## UniFi inspection and radio identity

`unifly` 0.10.0 was installed locally and connected to the UCK G2 Plus at `https://10.10.1.200`
(Network 10.6.106). Profile `home` uses the `default` site; its API key is in macOS Keychain
under service `unifly`, account `home/api-key`, not in this repository. The router at `10.10.1.1`
is separate. No Executor MCP connection was added because the CLI supplies the needed reads.

UniFi confirmed this station on SyNet-2G, authorized and not blocked, with power saving off.
The serving AP is U7 Pro `8c:30:66:6c:79:bc`, `10.10.1.95`, firmware 8.7.11.19419, channel 6,
20 MHz. Raw station counters after about eleven minutes showed 56 received packets / 40,856
received bytes at the AP, but zero transmitted packets, bytes, or attempts for this station.
These counters warrant investigation; they do not alone prove an AP defect.

The WLAN is WPA2/CCMP, 2.4 GHz only; client isolation, guest mode, MAC filtering, multicast
filtering, proxy ARP, fast roaming, PMF, U-APSD, and MLO are off. IoT optimization is on.
The Default LAN reports isolation off. Its IPv6 setting is off, which is not by itself an
explanation for failure of link-local Matter traffic or IPv4 ARP.

A board-only reconnect was attempted: the CLI's Integration API `RECONNECT` action failed
with `Invalid $.action value`; the supported legacy `kick-sta` command returned `rc=ok`.
The board logged link-down and disappeared from connected clients. It did not automatically
rejoin after the failed commissioning had rolled back its network credentials. No SSID, AP,
firewall, VLAN, or other client configuration was changed.

An extended diagnostic image was flashed at 2026-09-28 02:11:15 UTC, SHA-256
`d03519a179876afc90ee227806bfc97ae61bee09bec82455a04cd03f90429cde`.
It adds mDNS query/reply metadata and a one-shot read of the vendor station MAC. At boot,
`esp_wifi_get_mac` returned success and `20:6e:f1:12:a5:b0`, matching both the eFuse-derived
address and the earlier network-interface log. PHY reported `Some(DataCheckFailed)`; that enum
describes saved calibration-data validity, not an RF health test. The pinned stack performs
full calibration when no saved data is supplied. Both feature/default builds and clippy passed;
focused review found no driver ownership changes or payload/key logging.

Michael's next retry failed. The board again joined SyNet-2G and acquired `10.10.1.21`, but
logged no mDNS replies or incoming Matter UDP. The 177-second fail-safe expired. The serial
dropped-line counter remained 15 before and after this attempt. Fresh directed mDNS queries
and Mac pings failed; ARP remained incomplete. In this association UniFi did count two outbound
AP packets, so the earlier zero-counter observation is not a universal absence of AP traffic.

Read-only SSH access to the AP was obtained using its existing controller-managed credentials,
held in process memory. A 20-second capture on `wifi0ap0` showed the Mac's query and ARP requests
from both Mac and AP on the correct WLAN, plus fresh IPv4/IPv6 mDNS advertisements transmitted
by Stillair. This confirms continuing board transmission, not merely cached discovery or a
queued log message. The AP bridge forwarding table places the board MAC on `wifi0ap0`.
Neither the Mac nor the AP received an ARP reply. A temporary board-only neighbor entry on
the AP bypassed ARP for four unicast pings; all four failed. The entry was removed immediately
afterward. Subsequent source review found that the app does not enable smoltcp 0.13.1's
`auto-icmp-echo-reply` feature, so these ping failures do **not** establish unicast receive
failure. ARP/NDP and a directed mDNS query remain the useful probes. AP station counters showed
no transmit failures, but that is not proof that the ESP delivered those frames to its IP stack.
No persistent AP/WLAN setting was changed.

An AP-originated UDP unicast query, with a temporary neighbor entry bypassing ARP, received an
immediate valid 128-byte mDNS A/AAAA response. The otherwise identical query sent to
`224.0.0.251` timed out. This proves the app's unicast path works and narrows the failure to
incoming group traffic. Temporary multicast and broadcast rate changes from 1 to 6 Mbps did
not help and were restored to 1 Mbps. The legacy `mcastenhance 2` command read back as 0 and
had no demonstrated effect; 0 was explicitly restored. No controller setting was changed.

## Autonomous group-traffic diagnosis

Michael authorized continuing with tools and firmware while away, without further phone/button
steps. A temporary Wi-Fi-only baseline used the same pinned ESP driver, DHCP, and IPv6 setup,
with BLE/Matter absent and automatic ICMP echo replies enabled. Credentials were supplied
privately through the compiler child environment; its source and credential-bearing build
outputs were kept in a mode-0700 task directory outside the repository until final cleanup.
It performs no motor,
GPIO, or persistent-storage initialization. The fan image was saved for restoration.

Initial Mac pings succeeded, but this did **not** prove group reception: a later AP capture
showed the Mac sending unicast ARP to a cached MAC, which the board answered, while broadcast
ARP from the AP went unanswered. IPv6 neighbor discovery also failed. The Wi-Fi-only baseline
therefore reproduced the original group-traffic failure without Bluetooth.

A second scratch baseline counted Ethernet destination classes before passing unmodified
frames to Embassy. After DHCP, it counted three unicast frames and zero broadcast ARP, IPv4
multicast, or IPv6 multicast frames. Fresh broadcast probes did not increase group counts.
Two existing SyNet-2G devices, an Espressif-based thermostat and a TP-Link plug, also failed
broadcast ARP while answering ordinary unicast pings. The same broadcast-ARP tool received
two replies from the wired router, validating the probe path.

One U7 Pro restart was initiated through UniFi at **2026-09-28 02:33:49 UTC**, with its settings
unchanged. The same running board image reconnected and immediately began receiving group
traffic. Its counters reached 4,413 broadcast ARP, 777 IPv4 multicast, and 1,061 IPv6 multicast
frames while unicast remained functional. Mac IPv6 ping passed 2/2. Fresh forced-broadcast ARP
from the AP then received 2/2 replies from each of the board, thermostat, and plug.

This is direct before/after evidence of failed group delivery on the AP/WLAN, restored by the
AP restart without a firmware change. The internal AP failure mechanism and recurrence risk
are unknown. The observed failure reproduced without Matter or Bluetooth, and the same C6
target worked after the restart. Home's 2.4 GHz message did not identify this failure accurately.

## Successful Matter verification and final handoff

With Michael away, a scratch copy of the app seeded only its Wi-Fi network blob through the
pinned public persistence API. Credentials were supplied through a private compiler environment,
not source. The normal Matter, BLE, supervisor, and fan endpoint code ran unchanged. This let a
temporary local `@matter/nodejs-shell` 0.17.9 controller commission over IP without the phone.

At **2026-09-28 02:43:26 UTC**, commissioning completed: PASE, test attestation acceptance,
certificate installation, operational discovery, **IPv6 CASE**, and **CommissioningComplete**.
The board logged `Commissioning complete, fabric and network settings persisted`. The controller
found endpoint 1 as Fan revision 4 and read `productName="Stillair"`. FanControl reported Off,
zero percent, and forward direction. No motor command was sent.

The normal release image, without network seeding or diagnostic logging, was then flashed.
It booted with `Device is already commissioned`, rejoined SyNet-2G from NVS, and a fresh
controller process established another secure session and performed remote attribute reads.
This verifies persistence across an ESP restart and image replacement. The release also corrects
the stale hardware identity to version 2 / `PCB-01 V2`; that value was read back over Matter.
Optional unsupported attributes requested by the shell's `read all` correctly returned
UnsupportedAttribute; the advertised FanControl attributes read successfully.

The temporary fabric was removed remotely with status 0 at **02:46:41 UTC**. Since last-fabric
removal retains the network blob in this pinned stack, the temporary Matter data was then
cleared by erasing **only ESP NVS `0x9000..0xf000`**. This did not erase the application or touch
the external MCF EEPROM. The clean normal boot opened BLE commissioning again with
**3497-0112-332**. The post-reset MCF watchdog fault was cleared; after the 10-second hold,
`config check` passed and telemetry reported `idle_off`, `fault=null`, `on=false`,
`cmd_mrpm=0`, `duty=0`, and `config=verified`.

Final installed ELF: `firmware/app/target/riscv32imac-unknown-none-elf/release/stillair`,
SHA-256 **`463c78e2c9bbbf3abb1c2372fa00a664a52d697a7975583f8a7c4032429bdaaf`**.
Both workspaces passed formatting and clippy with warnings denied; all **234 host tests** passed,
and the release build passed. Diagnostic feature builds were also verified earlier in this work.
Credential-bearing scratch build outputs and the temporary controller's private state were
removed after testing; source and sanitized receipts remain outside/inside the repo as appropriate.

The original network blocker is resolved and automated Matter commissioning passed.
**Apple Home itself has not been retried after the AP fix because Michael was away.** Its final
confirmation remains the next user action before installation. Motor tuning and the previously
deferred physical qualification remain outside this bench session's scope.
